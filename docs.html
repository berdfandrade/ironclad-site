Using Ironclad

Everything you need to run a cluster, talk to it, embed the storage engine in your own program, and understand what it guarantees when things fail.

01Overview

Ironclad is a key-value store. Keys and values are arbitrary bytes. It supports three operations: GET, SET and DELETE. You can use it in three ways:

As a clusterRun ironclad-server on 3 or 5 machines. Data is replicated with Raft and survives the loss of a minority. As a clientTalk to the cluster with ironclad-cli, the async Rust Client, or any language that speaks the binary protocol. As a libraryOpen the LSM storage engine directly in your Rust program, with no network and no cluster.

It requires Rust 1.89 or newer (edition 2024). Docker is optional and only needed for the five-node demo.

02Quick start

Build the server and the CLI:

$ git clone https://github.com/berdfandrade/ironclad
$ cd ironclad
$ cargo build --release

A single node

Without --member flags the node forms a cluster of one, listening for clients on 127.0.0.1:6001:

$ ./target/release/ironclad-server --id 1 --data-dir ./data/single
$ ./target/release/ironclad-cli set hello world
OK
$ ./target/release/ironclad-cli get hello
world

Three nodes on localhost

The script starts N nodes. Node i serves clients on 127.0.0.1:600i and peers on 127.0.0.1:700i. Logs go to ./data/<id>/server.log. Ctrl-C stops every node.

$ scripts/local-cluster.sh 3
$ ./target/release/ironclad-cli -a 127.0.0.1:6001,127.0.0.1:6002,127.0.0.1:6003 status

Extra server flags can be passed through IRONCLAD_FLAGS, for example IRONCLAD_FLAGS=--storage-fsync scripts/local-cluster.sh 3.

Five nodes in Docker: the failover demo

$ scripts/failover-demo.sh

The script starts five containers and writes 5,000 records (set RECORDS to change that). It then kills the leader with SIGKILL, waits for a new election, restarts the old leader with its old data, and checks that every node reaches the same applied index.

== 3. killing the leader (node4) with SIGKILL
== 4. waiting for a new leader
new leader: node3 (term 2) after 1933 ms
== 6. verifying convergence
applied_index per node: 4004 4004 4004 4004 4004
all five nodes converged to the same state

03Running a server

Every node runs one ironclad-server process with its own data directory. Every node needs the full member list, including itself.

$ ironclad-server --id 1 --data-dir /var/lib/ironclad \
    --member 1=10.0.0.1:6001=10.0.0.1:7001 \
    --member 2=10.0.0.2:6001=10.0.0.2:7001 \
    --member 3=10.0.0.3:6001=10.0.0.3:7001
FlagDefaultMeaning
--idrequiredThis node's id. Non-zero and unique in the cluster.
--data-dirrequiredWhere the storage engine and the Raft log live.
--member—id=client_addr=peer_addr. Repeat once per member. Omit for a single node.
--listenown client_addrBind address for clients, when it differs from the advertised one (e.g. 0.0.0.0:6001).
--peer-listenown peer_addrBind address for other nodes.
--tick-ms50Raft tick interval in milliseconds.
--election-ticks10Election timeout in ticks, randomized between N and 2N (500–1000 ms by default). Heartbeats go out every tick.
--compact-threshold10000Compact the Raft log into a snapshot after this many applied entries.
--storage-fsyncoffAlso fsync the storage engine on every applied batch. Not needed for durability, since the Raft log is fsynced. Costs one extra fsync per batch.
Addresses in --member are advertised addresses. They go to clients in leader redirects, so they must be reachable from wherever clients run. In Docker Compose the client address is the host-mapped port and the peer address is the container name.

Cluster size

A cluster of N nodes stays available while a majority is up: 3 nodes tolerate 1 failure, 5 nodes tolerate 2. Membership is fixed at startup. Use an odd number of nodes, since an even number adds no extra tolerance.

Data directory

<data-dir>/
  raft/raft.state   term + vote, checksummed, replaced atomically
  raft/raft.log     snapshot header + log entries
  db/LOCK           exclusive lock: one process per directory
  db/MANIFEST       live SSTables + WAL replay start
  db/000042.wal     write-ahead log
  db/000041.sst     immutable sorted table

Starting a second process on the same directory fails immediately instead of corrupting it.

04CLI

$ ironclad-cli [-a ADDR[,ADDR...]] <command>

-a / --addr takes the client addresses of any subset of the cluster (default 127.0.0.1:6001). The CLI finds the leader by itself, so one address is enough. Listing more lets it keep working when that node is down.

05Consistency

Writes

A SET or DELETE returns OK only after the entry is in the Raft log of a majority of nodes, fsynced, and applied on the leader. A write acknowledged with OK survives any failure that leaves a majority alive.

Reads

ModeGuaranteeCost
Linearizable (default)Sees every write acknowledged before the read started.Served by the leader. It confirms its leadership with a quorum (ReadIndex), then waits until it has applied up to the commit index. No log entry is written.
Local (--local)Sees some earlier state. May be stale, never torn.Served by whichever node you are connected to, with no network round trip.

Exactly-once writes

Every write carries a (client_id, seq) pair. Each node remembers the last seq applied per client, and that record is stored in the same atomic batch as the data. A retried write with the same pair is acknowledged but not applied twice, even across a leader change. The Rust client and the CLI do this for you. client_id = 0 opts out.

A TIMEOUT means the outcome is unknown. The write may or may not have been committed. Retrying with the same seq is safe. Retrying with a new one may apply it twice.

Partitions

A leader that cannot reach a majority steps down by itself after an election timeout (check-quorum). Clients on the minority side then get NOT_LEADER or TIMEOUT, never a stale linearizable read. When the partition heals, the minority nodes catch up from the leader's log, or from a snapshot if the log was already compacted.

06Wire protocol

Clients talk to nodes over TCP using a small, versioned binary protocol. Any language can implement it. All integers are big-endian.

Framing

frame    = length:u32  body          length excludes itself
request  = version:u8=1  request_id:u64  op:u8  args
response = version:u8=1  request_id:u64  status:u8  payload
key, value = len:u32  bytes
string     = len:u32  utf-8

The response echoes the request_id. Requests on one connection run strictly in order, so a client may pipeline several requests and match the responses by id. For parallelism, open more connections.

Requests

OpCodeArguments
GET1consistency:u8 (0 = linearizable, 1 = local), key
SET2client_id:u64, seq:u64, key, value
DELETE3client_id:u64, seq:u64, key
PING4—
STATUS5—

Responses

StatusCodePayloadMeaning
OK0—Write committed, or ping answered.
VALUE1valueThe key exists.
NOT_FOUND2—The key does not exist.
NOT_LEADER3has_hint:u8 [addr:string]Retry on the hinted leader, or on another node if there is no hint.
BUSY4—Backpressure: nothing was done. Retry later.
TIMEOUT5—Outcome unknown. Retry with the same seq.
ERROR6message:stringInvalid request or internal error. Do not retry unchanged.
STATUS7text:stringReply to STATUS: key=value lines.

Limits

  • Keys: 1 to 65,536 bytes. Keys starting with byte 0x00 are reserved for internal metadata and rejected.
  • Values: up to 4 MiB.
  • Frames: up to 4 MiB + 65 KiB. Larger frames close the connection.

Example: PING

# request: length=10, version=1, request_id=1, op=4
00 00 00 0a  01  00 00 00 00 00 00 00 01  04
# response: length=10, version=1, request_id=1, status=OK
00 00 00 0a  01  00 00 00 00 00 00 00 01  00

07Rust client

The crate ships an async client built on Tokio. It is the same client the CLI uses.

use ironclad::client::Client;
use ironclad::protocol::Consistency;

let mut client = Client::new(vec![
    "127.0.0.1:6001".into(),
    "127.0.0.1:6002".into(),
    "127.0.0.1:6003".into(),
]);

client.set("user:123", r#"{"name":"Bernardo"}"#).await?;
let value = client.get("user:123", Consistency::Linearizable).await?; // Option<Bytes>
client.delete("user:123").await?;
let status = client.status().await?;                             // key=value text

What it handles for you

  • Leader discovery. It follows NOT_LEADER hints straight away, up to three times in a row. It moves to the next address when a node is unreachable or has no leader.
  • Retries. BUSY, TIMEOUT and connection errors are retried with exponential backoff from 20 ms up to 500 ms.
  • Exactly-once. Each Client picks a random client_id and increments seq per write, so retries are deduplicated by the cluster.
  • Deadline. op_timeout (10 s by default, public field) bounds each operation across all retries.

Errors

VariantWhen
ClientError::Unavailable { attempts, last }The deadline ran out. last is the last reason, e.g. no leader (election in progress).
ClientError::Server(msg)The server answered ERROR, e.g. an invalid key.
ClientError::Protocol(msg)The server sent something unexpected.

A Client uses one connection and runs one operation at a time. Use one client per task for concurrency.

08Embedded storage engine

The storage engine is a standalone LSM tree. You can use it as a local, crash-safe ordered map, with no Raft and no network.

use ironclad::storage::{Db, Options, WriteBatch};

let db = Db::open("./data/embedded", Options::default())?;
db.put("user:123", r#"{"name":"Bernardo"}"#)?;

let mut batch = WriteBatch::new();   // atomic: all or nothing
batch.put("a", "1");
batch.delete("b");
db.write(batch)?;

assert_eq!(db.get(b"a")?.as_deref(), Some(&b"1"[..]));
for entry in db.iter() {             // sorted, point-in-time view
    let (key, value) = entry?;
}

API

MethodDescription
Db::open(dir, opts)Open or create a database. Replays the WAL and fails if another process holds the directory.
put(key, value)Insert or overwrite one key.
delete(key)Remove one key (writes a tombstone).
write(batch)Apply a WriteBatch atomically: readers and crash recovery see all of it or none of it.
get(key)Option<Bytes>. Checks the memtables, then SSTables newest first, skipping tables whose bloom filter rules the key out.
iter()All live keys in order, from a consistent snapshot. Writes during iteration are not visible.
sync()fsync the WAL. Only needed with sync_writes: false.
flush()Write the memtable to an SSTable now.
compact()Merge all SSTables into one, dropping overwritten values and tombstones.
stats()DbStats: tables, table_bytes, table_entries, memtable_bytes, flushes, compactions, write_stalls.

Db is Send + Sync, so share it between threads behind an Arc. Flushes and compactions run on a background thread. Readers never wait for them.

Options

FieldDefaultMeaning
memtable_size4 MiBMemtable size that triggers a flush to an SSTable.
sync_writestruefsync the WAL on every write. With false, a process crash still loses nothing, but power loss may drop the most recent writes.
block_size4096Target SSTable data block size in bytes. Every block is checksummed.
bloom_bits_per_key10Bloom filter size, about a 1% false-positive rate.
compaction_trigger4Number of SSTables that triggers a background compaction.
Write stalls. If the memtable fills while the previous one is still being flushed, writers wait for the flush. This is backpressure, not an error. It is counted in write_stalls.

Status and metrics

ironclad-cli status (or a STATUS request) returns one key=value per line:

KeyMeaning
id, role, term, leaderWho this node is, whether it is leader, follower or candidate, and who it thinks leads (none during an election).
commit_indexHighest log index known to be on a majority.
applied_indexHighest index applied to storage. Equal on all nodes means converged.

snapshot_indexIndex the log was last compacted up to.

The output is plain text, so a scraper can turn it into Prometheus or any other format:

$ ironclad-cli -a 127.0.0.1:6002 status | grep -E '^(role|term|applied_index)='
role=follower
term=2
applied_index=4004

Logs and tracing

The server logs structured events with tracing to stderr: startup, elections, new leaders, snapshot installs and peer errors. The level is set with RUST_LOG (default info):

$ RUST_LOG=debug ironclad-server --id 1 --data-dir ./data/single

10Errors and backpressure

An overloaded node sheds load rather than queuing without bound. There are three layers, from the outermost in:

LimitDefaultWhen exceeded
Open client connections1024New connections wait in the TCP accept backlog.
Queue into the Raft loop16,384 eventsThe request is answered BUSY straight away. Nothing was done.
Per-request deadline5 sTIMEOUT: the request may still complete.

Inside the storage engine, a full memtable stalls writers until the previous flush finishes (see write stalls).

What a client should do

ResponseAction
NOT_LEADER with hintReconnect to the hinted address and resend.
NOT_LEADER without hintAn election is in progress. Try another node after a short pause.
BUSYBack off and retry.
TIMEOUTRetry with the same (client_id, seq).
ERRORFix the request. Retrying unchanged gives the same error.

11Durability and recovery

Crashes

Restarting a node after a crash needs no manual step. On startup it loads the latest snapshot and Raft log, opens the storage engine (replaying its WAL), then catches up with the cluster. It may receive missing entries from the leader, or a full snapshot if the leader already compacted them away.

  • Process crash (kill -9, panic): nothing acknowledged is lost.
  • Power loss: the Raft log is fsynced before any acknowledgement. The storage engine may roll back to an earlier batch. The applied index is stored in the same batch, so it rolls back too, and the missing entries are re-applied from the Raft log.

Torn writes and corruption

Every log record, SSTable block, manifest and Raft state file has a CRC32 checksum. On recovery the first invalid record is classified:

CaseWhat happens
Torn tail: the last record is cut short or zero-filledExpected after a crash mid-append. The valid prefix is kept and the tail is truncated.
A bad record followed by more dataA crash cannot produce this. The node refuses to start with a Corruption error naming the file, and nothing is silently discarded.
A bad SSTable block on readThe read fails with Corruption rather than return wrong data.

Files that change (the manifest and the Raft state) are replaced atomically: write a temporary file, fsync, rename, fsync the directory. A crash leaves either the old version or the new one.

A node that refuses to start leaves its files untouched so they can be inspected. The rest of the cluster keeps serving as long as a majority is up.

12Testing

$ cargo test --release                       # everything
$ cargo test --release --test raft_sim       # deterministic Raft simulation
$ cargo test --release --test cluster        # real processes, real sockets
$ cargo test --release --test storage        # crash, corruption, concurrency
$ cargo bench                                # storage engine micro-benchmarks
SuiteWhat it proves
raft_sim60 seeded runs on a virtual clock with message loss, reordering, partitions and crashes. Each step checks election safety, state-machine safety, durability of acknowledged writes and read linearizability. A failure replays from its seed.
clusterThe failover demo as a test: five real server processes, the leader killed with SIGKILL and restarted, then convergence checked.
storageRecovery after simulated crashes and torn writes, detection of flipped bytes, readers never seeing a partial batch under concurrent writes and flushes, and property tests (Proptest) against a BTreeMap model.

13Limitations

These are deliberate scope cuts, each documented in ADR 0005 with what it would take to lift it.

  • Static membership. Nodes cannot be added or removed while the cluster runs.
  • No security on the wire. Neither port authenticates or encrypts. Run Ironclad on a private network.
  • Snapshots are sent as one message, built in memory, which limits practical dataset size.
  • No pre-vote. A node rejoining after a partition forces one extra, harmless election.
  • Full-merge compaction rewrites all data each time. Client session records are never expired.
  • No range scans over the network. Only the embedded engine offers iter().
