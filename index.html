RUST · LSM-TREE · RAFT

A key-value store that doesn’t lose data when a node goes down.

Ironclad is a distributed, embeddable key-value store written in Rust: persistent storage with its own write-ahead log, replication through Raft consensus, and crash recovery that is tested on purpose.

Packages for 64-bit Linux (amd64). The snap and the APT repository update with every release.

Any distribution with snapd

$ sudo snap install ironclad

$ ironclad set hello world
OK

Ubuntu 22.04+ and Debian 12+

$ sudo install -d -m 0755 /etc/apt/keyrings
$ curl -fsSL https://berdfandrade.github.io/ironclad-site/apt/ironclad.gpg | sudo tee /etc/apt/keyrings/ironclad.gpg > /dev/null
$ echo "deb [arch=amd64 signed-by=/etc/apt/keyrings/ironclad.gpg] https://berdfandrade.github.io/ironclad-site/apt stable main" | sudo tee /etc/apt/sources.list.d/ironclad.list
$ sudo apt update && sudo apt install ironclad
$ sudo systemctl enable --now ironclad   # single node; cluster: /etc/default/ironclad

Same package, without adding the repository (no automatic updates)

$ curl -fLO https://github.com/berdfandrade/ironclad/releases/latest/download/ironclad_amd64.deb
$ sudo apt install ./ironclad_amd64.deb
$ sudo systemctl enable --now ironclad

Rust 1.89 or newer

$ git clone https://github.com/berdfandrade/ironclad
$ cd ironclad && cargo build --release
$ ./target/release/ironclad-server --id 1 --data-dir ./data
THE LIFE OF A WRITE

A SET looks simple. Underneath, it takes seven steps.

All of it concurrent, and without corrupting data — even if the machine dies halfway through.

  1. 01ReceiveThe request arrives over the binary TCP protocol, with every length checked.
  2. 02ValidateThe command engine validates the key and serializes the command.
  3. 03LogThe leader appends the entry to the Raft log, with a CRC32 checksum.
  4. 04ReplicateFollowers receive the entry, write it to disk and acknowledge it.
  5. 05CommitOnce a majority has it on disk, the entry is committed.
  6. 06ApplyThe WAL and the MemTable are updated in a single atomic batch.
  7. 07ReplyThe client gets OK — and the data survives a crash.
ARCHITECTURE

Five layers, each with one job.

The core — storage engine and consensus — is written by hand. Libraries only play supporting roles: Tokio, Bytes, Tracing.

Client API / TCPbinary protocol · connections · parsing
Command Enginevalidation · serialization · pipeline
Consensus LayerRaft · leader election · replication
Storage Engine the heartWAL · MemTable · SSTables · Bloom filters
Persistence & Recoverychecksums · snapshots · compaction
THE DEMO

Kill the leader. The data is still there.

  1. Start five nodes.
  2. Write thousands of records.
  3. Kill the leader abruptly.
  4. Watch a new leader get elected.
  5. Bring the old node back.
  6. Verify that every node converged to the same state.

All of it proven by automated tests, not a screenshot.
